Core feature

Trigger Volumes

QuestLines plugs into Hytale's built-in Trigger Volumes system — invisible 3D regions that fire on enter/exit. Admins author the volumes externally (Hytale's in-world tools, prefabs, or the /triggervolume console command); QuestLines exposes them to the quest engine through trackers, requirements, actions, and text variables, and adds two custom volume types that run QL actions or check QL requirements directly.

How It Works

QuestLines does not ship its own trigger-volume editor, wand, or JSON config. The Hytale plugin already owns the spatial index, shape codecs, and persistence — QuestLines just plugs in via a thin bridge (integrations/triggervolumes/TriggerVolumesBridge). A global listener subscribed to TriggerVolumeEvent feeds enter/exit events to the named tracker system.

When the plugin boots, the bridge registers two custom volume types with Hytale's trigger-volume plugin so a volume can carry QuestLines behaviour directly:

Hytale type idKindPurpose
questlines:actionsEffectCarries a List<String> of QL action strings. On fire, runs them against the triggering player.
questlines:requirementConditionCarries a single Requirement string; delegates to the requirement engine. Supports the leading ! negation operator.

Both no-op gracefully for non-player entities, so the same effect or condition can sit on a volume whose target types include NPCs or projectiles.

Custom Volume Types

Attach these to a volume statically (via Hytale's in-game tool) or through its JSON. A questlines:actions effect: 

{
  "Type":   "questlines:actions",
  "Event":  "ENTER",
  "Actions": [
    "chat:Welcome to the test zone",
    "giveitem:Map:1",
    "track:visited:volumeenter:[my_zone]"
  ]
}

Actions is a flat list of standard QL action strings — the full chat:, giveitem:, delay:, track:, startEscort:, if: … catalog works exactly as it does in a quest response. Variable substitution runs first via the text formatter.

A questlines:requirement condition: 

{
  "Type":        "questlines:requirement",
  "Event":       "ENTER",
  "Requirement": "questCompleted:tutorial"
}

Any QL requirement is valid — hasTag:vip, nearPosition:100:64:200:10, track:foo:5, !variable:dead:greater:0, etc.

Trackers

Enter/exit events feed the named tracker system, so you can count zone visits like any other objective. Targets, excludes, location gates, and world gates all use the standard track: syntax.

TypeValueDescription
volumeentervolume idFires when a player enters the volume.
volumeexitvolume idFires when a player exits the volume.
 
track:visited:volumeenter:[my_zone]
track:safehouse_visits:volumeenter:safehouse:loc:100:64:200:50
track:left_dungeon:volumeexit:[dungeon_*]:exclude:[dungeon_lobby]

Requirements

FormatDescription
inVolume:volumeIdPlayer is currently inside the named enabled volume.
inVolume:[a,b,c]Inside any of the listed volumes. Patterns support * wildcards.
volumeTag:keyInside any volume carrying a tag with this key. Wildcards allowed.
volumeTag:key:valueInside any volume with the matching key=value pair.

Both are contextual — skipped during HUD requirement resolution so a quest doesn't lock just because the player walked out of a zone. Use them on response gates, page requirements, or if: actions.

Actions

These mutate the world's trigger-volume manager. All are safe to call from any action context (they run on the world thread); the spatial index rebuilds on the next tick.

FormatDescription
createVolume:id:box:x1:y1:z1:x2:y2:z2[:enter:[a;b;c]][:exit:[a;b;c]][:tags:[k=v,k2]]Register a new box-shaped player-targeted volume at the given world coords. Coords support ~-relative syntax.
createVolume:id:sphere:cx:cy:cz:radius[:enter:[a;b;c]][:exit:[a;b;c]][:tags:[k=v,k2]]Sphere variant.
deleteVolume:idUnregister the volume from the player's current world.
enableVolume:id / disableVolume:idToggle the volume's enabled flag.
modifyVolumeTags:id[:add:[k=v,k2,k3=v3]][:remove:[k4,k5]]Add/remove tags; fires synthetic tag-added/tag-removed events so conditions re-evaluate.

Notes on createVolume:

  • Action lists inside enter:[...] / exit:[...] use ; as the separator so individual actions keep their : delimiters intact — e.g. enter:[chat:Hello;giveitem:Map:1;track:visited:volumeenter:[id]].
  • The volume is persisted automatically by Hytale's trigger-volume codec — it survives server restarts. Use deleteVolume: to clean up.
  • Created volumes default to player target type and enabled. For advanced configurations (cylinder shape, cooldowns, conditions, NPC target types, etc.) author the volume statically via Hytale's tools.
  • The action attaches questlines:actions effects internally for enter/exit, so the resulting volume looks identical to a statically-authored one.
